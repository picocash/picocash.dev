How it works

A mint issues blind-signed bearer tokens against stablecoins held in an on-chain vault. Every token carries a proof anyone can verify without contacting the mint.

01 — MINT

Deposit once

Send stablecoins to the mint's vault with a memo binding the deposit to your quote. The mint blind-signs secrets it never sees — the resulting tokens are yours alone.

More tech info
  1. Quote. POST /v1/mint/quote {amount, unit} → the mint returns a fresh 32-byte quote_id and a deposit instruction: the vault address, the TIP-20 token, and memo = quote_id.
  2. Deposit. You call the token's transferWithMemo(vault, amount, memo) on Tempo — an ordinary TIP-20 transfer whose bytes32 memo is your quote id. The vault holds the funds; the mint holds no keys to them that could skip the vault's rules.
  3. Observation. The mint watches the token's TransferWithMemo events with to = vault. An event whose indexed memo equals an open quote id and whose amount covers the quote flips that quote to PAID. No other signal is accepted — the chain is the only oracle.
  4. Blinding. Your wallet picks secrets x, computes Y = hash_to_curve(x), blinds them as B_ = Y + r·G, and sends only B_ with the quote id: POST /v1/mint {quote_id, outputs}.
  5. Signing. Inside one DB transaction the mint marks the quote issued, records each B_ (single-use), and returns C_ = k·B_ with a DLEQ proof that the same key k signed it. The mint never sees x or Y.
  6. Unblinding. The wallet computes C = C_ − r·K. The proof (x, C) is the token; anyone can check the DLEQ against the mint's published key K, offline.
One quote ↔ one memo ↔ one deposit transaction ↔ one set of blind signatures. The link is the 32-byte quote_id, visible in the transfer's memo on-chain and in the mint's issuance record — but it never appears in the tokens themselves, which is what makes later spending unlinkable. PIP-02 · PIP-00
02 — PAY

Spend in milliseconds

Services verify tokens offline via DLEQ proofs and settle asynchronously. Credentials are cryptographically bound to each challenge, so interception buys nothing.

More tech info
  1. Challenge. The service answers an unpaid request with 402 and an MPP challenge: amount, unit, its allow-listed mints and keysets, a 32-byte nonce, and optionally its P2PK pubkey.
  2. Bind. The agent swaps held tokens at the mint into fresh ones whose secrets are ["PC-BIND", {nonce, realm, salt}] — the secret itself commits to this challenge. Tokens a human pre-locked to the service's key (PIP-08) are presented as-is instead.
  3. Credential. Proofs summing to exactly the amount, each with its DLEQ payload {e, s, r}, travel in the Authorization: Payment … header.
  4. Six offline checks (~45 ms). Challenge single-use → mint/keyset/unit allow-listed → binding → exact amount and valid denominations → DLEQ per proof against the cached keyset → no duplicate Y. No call to the mint, no call to the chain.
  5. Settle. The service swaps the proofs at the mint for ones only it knows — that swap is the double-spend check and the moment of finality. By default it happens before success is returned; a service can opt into accept-then-settle.
Nothing in this path touches Tempo. The service learns that a valid token from an allowed mint paid this exact challenge — not who deposited, not which deposit. PIP-05
03 — MELT

Exit on-chain

Burn tokens, receive stablecoins from the vault. The vault publishes its outstanding supply on-chain — solvency is checked with one eth_call, not trust.

More tech info
  1. Quote. POST /v1/melt/quote {amount, unit, to} → a 32-byte melt_id, the payout address, and the flat melt fee (always ≤ the vault's on-chain maxMeltFee).
  2. Burn first. POST /v1/melt {melt_id, inputs} with proofs summing to amount + fee. In one DB transaction the mint writes every Y to the spent ledger and records the debt (PENDING) — before any chain call.
  3. Payout. The operator key calls vault.ecashMelt(to, amount, meltId). The vault transfers the token to to and sets meltPaid[meltId] = true; a second call with the same id reverts, whatever the mint's database says.
  4. Crash-safe. If the mint dies between burn and payout, the quote is OWED; re-posting the same inputs retries, and the mint first asks the vault meltPaid(meltId) so a payout that landed is never repeated.
  5. Attestation. Separately, the operator publishes outstanding = issued − spent via vault.publishOutstandingSupply under a policy fixed at deployment; miss the interval and the vault refuses new deposits until it is published.
One melt quote ↔ one melt_id ↔ one ecashMelt transaction, enforced by the contract, not by the server. PIP-03 · PIP-04

The exit guarantee — every clause on-chain

The contract cannot pause payouts. Each melt pays out exactly once. The fee to exit is capped by the vault's committed ceiling. And raising that cap — like rotating the operator key — takes the vault's public timelock (two days on the testnet vaults). Verify it all before depositing a cent.

The project

Everything is open source under Apache-2.0, live on Tempo's Moderato testnet, and under RFC — design feedback is the most valuable contribution right now.

The picocash specs — PIP-00 through PIP-08 plus published test vectors. A pip is a seed: small specifications you can grow an implementation from. The open design questions are up for debate in Discussions — start there.
